# Static rollback

Before upload record the previous release revision/hash, exact changed file list,
a recoverable backup outside the public root, protected paths and recovery owner.

If assets, routes, forms or acceptance fail, stop further uploads. Keep sanitized
symptoms and the failed release identity. Obtain explicit approval to restore the
exact public file scope from the prior artifact. Remove only newly introduced
files listed in that failed release and authorized for cleanup. Preserve
.well-known, unrelated roots, application runtime and user-generated data.

Do not treat database, DNS, TLS or runtime recovery as file rollback. Use their
separate owners and procedures when relevant. Never unpack an unreviewed archive
over the account home directory.

Repeat prior baseline root, route, asset/hash, MIME, TLS, redirect and form checks.
Record what is restored, what is cached and what still fails. Retain both release
identities; fix forward only after the failure is understood and reviewed.
