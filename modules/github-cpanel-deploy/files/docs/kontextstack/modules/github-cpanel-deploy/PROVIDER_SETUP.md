# Provider and approval procedure

Inspect the actual GitHub environment and cPanel secure-transfer controls. Record the exact branch, environment, reviewer policy, allowed deployment branches and bypass settings; separately authorize their configuration. Required reviewer availability depends on repository visibility and plan. Configure two distinct identities for split delivery and test server-enforced root confinement privately: a directory string alone is insufficient. Use only FTPS with valid certificate verification; if the host cannot support it, stop for a separately reviewed transport adaptation. Store only delivery credentials in the protected environment, with names STATIC_USER/STATIC_PASSWORD and APP_USER/APP_PASSWORD adapted if needed. Database, session, OAuth and administrator secrets stay outside GitHub delivery. Prepare a prior artifact and rollback references, then show the exact revision, manifest hash, destination identities/roots, dependency evidence and any restart effect for release approval. Dispatch that approved revision only. Verify static bytes/markers and Node release identity plus signed-out protection, retrying boundedly for asynchronous restart. File upload, runtime restart, separate migrations, hosted checks and owner acceptance are distinct states. Do not repeat failed smoke or partial transfer blindly.

Every action needs exact target, effect, owner, explicit approval, expected result, verification and recovery. Actual provider labels must be inspected. Paste non-secret evidence only; remove credentials, environment values, private keys, customer records and production rows. Review screenshots before retention.
