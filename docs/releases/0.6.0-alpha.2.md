## Scope and limits

See [the composition matrix](../architecture/COMPOSITION_VERIFICATION.md),
[data/auth review](../architecture/DATA_AUTH_PORT.md), and
[deployment/operations review](../architecture/DEPLOYMENT_OPERATIONS_PORT.md).
The original ContextStack specification and source revisions remain the primary
implementation trace; supporting evidence provided reusable operating patterns
only. No React/Vite/Express predecessor preset was promoted.

The toolkit remains local-first and filesystem-only: `network: false`, no
executable module commands, confined writes, no automatic overwrite. Inert
project templates are adapted by Codex before project-owned checks or approved
provider actions. The supplied durable auth adapter is a deliberately compact
serialized design; a selected production workload and MariaDB host still require
project-specific rehearsal. Real DNS/Google/cPanel/backup configuration and
production load are not certified by these local fixtures. The ContextKraft
build retains its pre-existing non-blocking large-chunk advisory.

## Owner approval and remaining release steps

Implementation and local gates are complete. Phase 6's live guide gate and Phase
7's published-package/live-origin confirmation remain pending; the initiative
must not be reported fully released yet.

The requested approval covers this concrete sequence:

1. Merge the reviewed toolkit changes, create the immutable alpha.2 tag/release,
   and publish the exact tested tarball to npm **`next`** with public access.
   Keep **`latest=0.5.1`**. Check registry identity/integrity and independently
   install the published package; stop if it differs from the approved tarball.
2. Record the verified publication in ContextKraft's reviewed snapshot: change
   `publication.status` from `candidate` to `published`, and `npmIntegrity` from
   `null` to the exact SHA-512 above. No guide content, module versions, provider
   settings, dependencies or schema are changed by activation.
3. Run the publication verifier, full checks, build and browser verification;
   commit/push the activation record and merge the reviewed ContextKraft change
   through its normal cPanel production workflow. This refreshes marketing and
   application artifacts because both serve the shared guide UI.
4. Verify canonical live origins, exact versions, direct guide routes,
   reload/provider pause and the marketing API boundary. Report the actual
   deployment commit and workflow result. A successful package publish alone
   does not complete this step.

Preserve prior application and marketing artifacts. For a failed guide release,
use ContextKraft's separate file rollback procedures; do not restore databases,
change identity configuration or run migrations. Downstream project/provider
authority is never granted by publishing the toolkit or completing a guide.
